# ADR-0007: Outbox 발행은 폴러 방식으로 하고, CDC 는 진화 경로로 남긴다

- 상태: 채택
- 날짜: 2026-08-19
- 관련: 설계 문서 §7.1

## 맥락
상태 변경과 이벤트 발행을 원자적으로 묶어야 한다. dual-write("DB 커밋 후 Kafka 발행")는 발행 직전
크래시에서 이벤트를 잃고, 순서를 뒤집으면 롤백 시 유령 이벤트가 남는다. 두 저장소에 걸친 쓰기는
2PC 없이는 원자적일 수 없고, 2PC 는 이 규모에서 비용이 이득을 넘는다.

## 결정
Transactional Outbox 를 쓴다. 상태 전이 · 상태 이력 · 한도 차감 · `OUTBOX_EVENT` INSERT 를
`PaymentProcessingService.validate()` 의 **하나의 로컬 트랜잭션**에 넣고, 별도 스케줄러
(`OutboxPoller`)가 `STATUS='NEW'` 행을 Kafka 로 내보낸다.

- 전달 보장은 **at-least-once**. 발행 성공 후 상태 갱신 전에 죽으면 재발행된다. 중복은 소비자 멱등성
  (inbox + 비즈니스 키 UNIQUE, §7.2)이 흡수한다. 유실은 어떤 하위 장치로도 복구할 수 없으므로,
  둘 중 하나를 골라야 한다면 중복 쪽이다.
- 다중 인스턴스에서는 `FOR UPDATE SKIP LOCKED` 로 행을 claim 해 같은 이벤트를 두 폴러가 집지 않게 한다.
  **Oracle 은 `FETCH FIRST ... ROWS ONLY` 와 `FOR UPDATE` 를 한 질의에 함께 쓸 수 없다(ORA-02014).**
  실제로 확인한 제약이며, 정렬·제한은 서브쿼리에서 하고 잠금은 바깥 질의에서 거는 2단 구조로 우회했다.
- Kafka 발행을 DB 트랜잭션 안에서 수행한다. 행 잠금을 발행이 끝날 때까지 쥐어 중복 발행 창을 좁히기 위함이며,
  대신 배치 크기(100)와 발행 타임아웃(10s)을 작게 유지해 트랜잭션이 길어지지 않게 한다.

## 기각한 대안
- **Kafka 트랜잭션 + DB 트랜잭션으로 2PC 흉내**: 두 시스템의 커밋 시점을 정렬할 수 없어 결국 동일한
  틈이 남는다. 복잡도만 오른다.
- **Debezium CDC**: 실무에서는 우수하다 — 폴링 지연이 없고 DB 부하도 적다. 다만 Kafka Connect 클러스터,
  커넥터 설정, 스키마 관리, LogMiner/XStream 권한 같은 운영 요소가 붙는다. 이 프로젝트가 증명하려는 것은
  "정합성 설계를 이해한다"이지 "Connect 를 운영할 수 있다"가 아니다.
  **진화 경로**: `OUTBOX_EVENT` 테이블 구조를 그대로 두고 폴러를 끄면 CDC 커넥터로 교체된다.
  이벤트 스키마와 파티션 키(`AGGREGATE_ID`)를 지금부터 CDC 가 그대로 쓸 수 있는 형태로 잡아 두었다.

## 결과
- 한계: 폴링 주기(기본 5초)만큼 발행이 지연되고, 유휴 시에도 주기적 쿼리가 돈다. 지연이 문제가 되면
  주기를 줄이거나 CDC 로 옮긴다.
- `payment-core` 안에서 `KafkaTemplate` 직접 호출은 금지한다(CLAUDE.md 불변식 3). 발행 경로는
  `OutboxPoller` 하나뿐이며, 이 규칙이 깨지면 outbox 보장이 조용히 사라진다.
