# ADR-0006: 일일 한도 차감은 비관적 락(SELECT ... FOR UPDATE)으로 한다

- 상태: 채택
- 날짜: 2026-08-19
- 관련: 설계 문서 §5.2

## 맥락
`PAYMENT` 의 상태 전이는 낙관적 락(`VERSION` 컬럼)으로 보호한다. 그런데 `DAILY_LIMIT` 차감은 성격이 다르다.
차감은 전형적인 read-modify-write 다: 현재 사용액을 읽고, 여유가 있는지 판단하고, 더한 값을 쓴다.

두 요청이 같은 계좌를 동시에 건드릴 때 무슨 일이 벌어지는지가 두 락의 차이다.

## 결정
`DailyLimitRepository.findForUpdate()` 에 `@Lock(PESSIMISTIC_WRITE)` 를 걸어 행을 잠근 뒤 차감한다.

근거 세 가지:

1. **정확성이 가용성보다 우선이다.** 낙관적 락은 충돌을 "나중에" 발견하고 재시도로 푼다. 재시도가 실패하면
   사용자에게는 아무 이유 없는 이체 실패로 보인다. 한도는 잔액과 달리 "잠깐 기다리면 되는" 자원이라
   기다리는 편이 낫다.
2. **경합이 실제로는 낮다.** hot row 는 (계좌, 날짜) 단위다. 한 기업 계좌가 같은 순간에 여러 이체를
   내보내는 경우는 배치 전송 정도이고, 그때도 잠금 구간은 UPDATE 한 줄이라 매우 짧다.
   경합이 전체가 아니라 계좌별로 분산된다는 점이 핵심이다.
3. **낙관적 락은 여기서 정확하지도 않다.** 차감 실패를 재시도로 처리하면 "몇 번까지 재시도할 것인가"가
   곧 "한도를 얼마나 정확히 지킬 것인가"가 된다. 돈이 나가는 판단에 그런 확률적 요소를 넣지 않는다.

행이 없는 첫 거래는 INSERT 후 잠근다. 동시 INSERT 는 PK 충돌로 하나만 성공하고, 진 쪽은 이긴 쪽이 만든
행을 다시 잠근다 — 여기서도 최종 방어선은 애플리케이션 코드가 아니라 DB 제약이다.

## 기각한 대안
- **낙관적 락 + 재시도**: 위 3번. 또한 재시도가 트랜잭션 전체(상태 전이 + 아웃박스 INSERT)를 되감아야 해서
  비용이 잠금 대기보다 크다.
- **원자적 UPDATE 한 방** (`UPDATE ... SET USED = USED + :amt WHERE USED + :amt <= LIMIT`): 잠금 없이 정확하고
  가장 빠르다. 실제로 매력적인 선택지다. 채택하지 않은 이유는 (a) 갱신 행 수 0 이 "한도 초과"인지
  "행 없음"인지 구분되지 않아 분기 로직이 SQL 밖으로 새고, (b) 한도 정책이 복잡해지면(구간별 한도, 건당/일일
  이중 한도) 한 문장으로 표현할 수 없게 되기 때문이다. 성능 문제가 확인되면 이 방향으로 옮긴다.
- **분산 락(Redis 등)**: 인프라가 하나 더 늘고, DB 트랜잭션과 락의 경계가 어긋나는 순간 정합성이 깨진다.
  같은 DB 안에서 해결되는 문제를 밖으로 꺼낼 이유가 없다.

## 결과
- `DAILY_LIMIT` 은 `CK_DAILY_LIMIT_RANGE CHECK (USED_AMOUNT >= 0 AND USED_AMOUNT <= LIMIT_AMOUNT)` 로
  애플리케이션 버그까지 DB 가 막는다.
- 잠금 구간 안에서 외부 호출(Kafka/HTTP)을 하지 않는다는 규칙을 함께 지킨다.
