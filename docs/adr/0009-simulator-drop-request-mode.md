# ADR-0009: 시뮬레이터에 `DROP_REQUEST` 모드를 추가한다

- 상태: 채택
- 일자: 2026-08-20
- 관련: `docs/payment-platform-design.md` §5.4 · §7.3 · §8 시나리오 #3

## 맥락

설계 §5.4 의 모드 표에는 `DOWN`("큐에서 소비 중단")이 있고, §8 시나리오 #3 은
**"`DOWN` 후 복구 → UNKNOWN → inquiry → FAILED 확정"** 을 기대한다.

그런데 `DOWN` 을 표 그대로 "리스너 정지"로 구현하면 시나리오 #3 이 성립하지 않는다.
정지 상태에서 pacs.008 은 큐에 **쌓여 있다가** 복구 시점에 그대로 소비되어 정상 처리된다.
즉 결과는 "미처리 확정(FAILED)"이 아니라 "늦은 정상 처리(CLEARED)"가 된다.

두 모드는 검증 목적이 서로 다르다.

| 목적 | 필요한 동작 |
|---|---|
| 재시도 · DLQ · 운영 알림 (§5.4) | 메시지가 **큐에 남아** 소비만 멈춘다 |
| 시나리오 #3 "실제로 미처리" (§8) | 메시지가 **유실**되어 상대방이 받은 적이 없다 |

## 결정

모드를 두 개로 나눈다.

- **`DOWN`** — `JmsListenerEndpointRegistry` 로 `CLR.REQ` 리스너를 정지한다. 메시지는 큐에 쌓이고
  복구하면 그대로 처리된다. (§5.4 원안 유지)
- **`DROP_REQUEST`** — 수신은 하되 **아무 기록도 남기지 않고 버린다.** 상대 은행은 그 이체를 받은 적이 없다.
  이후 pacs.028 inquiry 에 `RJCT / NOOR`(No Original Transaction Received)로 답한다.

시나리오 #3 은 `DROP_REQUEST` 로 재현한다.

## 근거

`NOOR` 는 ISO 20022 External Status Reason 코드로 "원거래를 받은 적 없음"을 뜻한다.
inquiry 가 이 답을 받았을 때만 게이트웨이는 `FAILED` 를 **확정**할 수 있고, 그때 비로소
"새 msgId 로 재송신해도 안전하다"는 정책적 판단이 가능해진다(§7.3). 이 경로를 테스트로 강제하려면
"응답이 없다"가 아니라 "받은 적 없다고 답한다"를 만들어낼 수 있어야 한다.

`DOWN` 을 유실 모드로 재정의하지 않은 이유: 큐에 쌓이는 상황(백프레셔, DLQ, 소비 지연 알림)은
Phase 6 에서 따로 검증해야 하는 실제 시나리오이고, 그걸 표현할 모드가 사라지면 안 된다.

## 결과

- 모드 표에 `DROP_REQUEST` 한 줄이 추가된다. README 와 §5.4 대비 차이로 명시한다.
- `DROP_REQUEST` 에서도 시뮬레이터는 **처리 기록을 남기지 않는다** — EOD CSV 에도 나오지 않는다.
  이것이 Phase 5 대사에서 `MISSING_AT_CLEARING` 이 아니라 정상(양쪽 다 미처리)으로 잡히는 근거다.
